## Assumptions and open risks

- One-time/manual newsletter source IDs use the newsletter ID. Recurring occurrences append the scheduled timestamp so each occurrence gets immutable audience/content and a distinct provider idempotency key. This preserves existing recurring behavior without dynamically reevaluating an already-started occurrence.
- Selected audience sources must load completely before first materialization; transient source failures return `audience_unavailable`.
- Queued content is immutable. Newsletter/blog edits after materialization do not alter the existing delivery source.
- Retry attempts are capped at five with 1/2/4/8-minute backoff before `dead`; the retry design assumes scheduler cadence keeps attempts inside [Resend's documented 24-hour idempotency window](https://resend.com/docs/dashboard/emails/idempotency-keys).
- Existing `NEWSLETTER_CRON_SECRET` ownership is reused to process both admin and blog ledger rows. Blog publish requests only materialize; no scheduler/provider/rate-limit change was made.
- Production migration/cron execution was not performed. Approved staging interruption/retry proof remains operator-owned, so `advisor-plans/README.md` row 030 stays `TODO`.
- Spec remains in `factory/specs/active/masest-030.md` for review.
