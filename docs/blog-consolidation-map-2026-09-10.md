## 5. Redirect mechanism (verified against the actual build)

**Mechanism:** a static Cloudflare Pages [`_redirects`](https://developers.cloudflare.com/pages/configuration/redirects/)
file, written once per build at `dist/_redirects` by `tools/cf-build.mjs:142`:

```js
writeFileSync(join(OUT, '_redirects'), renderIndustryRedirects(industryApplications));
```

`renderIndustryRedirects()` (`tools/build-industry-pages.mjs:40`) currently only understands
**industries-to-industries** redirects. It reads a `redirect_from: string[]` array off each
entry in `data/industry-applications.json` (a repo-owned config file, not CMS content) and
emits one line per retired slug:

```
/industries/<retired-slug> /industries/<current-slug> 301
```

Example from the live file (`git blame`-verified, not hypothetical):
```
/industries/schools-universities /industries/education 301
/industries/marine-marinas-boatyards /industries/marine 301
```

That's the exact syntax needed: `<source-path> <destination-path> <status-code>`, one per line,
space-separated, source and destination absolute from the site root. Cloudflare Pages applies
these before serving, in file order, first match wins.

**Two things this proposal needs that don't exist yet:**

1. **A generalized redirect renderer.** The current function only emits `/industries/* →
   /industries/*`. Blog-to-industries, blog-to-products, blog-to-resources, and blog-to-
   comparisons redirects (which is everything in this plan) need either a second render
   function alongside `renderIndustryRedirects` — call it `renderBlogRedirects` — whose output
   gets concatenated into the same single `writeFileSync(join(OUT, '_redirects'), …)` call at
   `cf-build.mjs:142` (it currently overwrites, not appends, so both renderers must feed one
   call), or a generic renderer that takes `{from, to}` pairs directly and is fed by both
   config sources.

2. **A repo-owned home for the `redirect_from` data — not `blog.json`.** The industries
   pattern stores `redirect_from` on the entries in `data/industry-applications.json`, which is
   a repo-owned config. Blog content is different: `data/content/blog.json` is a CMS/Supabase
   snapshot that a production deploy **overwrites from Supabase**, and retiring a post happens
   by removing/archiving it in the CMS, not by editing this file. `tools/build-blog.mjs`
   (lines ~552–558) actively **prunes** `blog/<slug>.html` for any slug no longer present in
   the current `blog.json` — so the moment a post is retired in the CMS, its old URL 404s on
   the very next build unless a redirect rule exists independently of that snapshot. Practical
   implication: the `redirect_from` mapping for blog posts must live in a small repo-owned file
   (e.g. a new `data/blog-redirects.json`, structurally: `[{"from": "old-slug", "to":
   "/industries/construction"}, ...]`) that survives CMS snapshot overwrites, not as a field
   added to the blog post objects themselves.

Verified there is no other redirect path in this codebase: no `wrangler.toml`/`wrangler.jsonc`
redirect rules at the root, and `functions/products/_middleware.js` (the only `_middleware.js`
in the repo) handles product-page pricing/JSON-LD injection and a SKU alias
(`crhd` → `cr-hd`), not URL redirection — it is not a viable place to add blog redirects without
scope-creeping a pricing middleware into routing.
